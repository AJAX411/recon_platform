# Instrucciones permanentes — Recon Facial

Estas instrucciones rigen el desarrollo de backend y frontend en `recon_platform`. Antes de trabajar, contrastar la tarea con el **Contexto Maestro v1.7 OFICIAL, vigente desde 25/10/2026**, y con las resoluciones arquitectónicas posteriores formalmente aprobadas. Una resolución puntual refina su ámbito; no constituye por sí sola una nueva versión del baseline. Usar el Documento principal para requisitos y trazabilidad académica, y el código y las pruebas para describir lo que realmente existe. El análisis del proyecto didáctico del profesor es referencia técnica, no autoridad funcional ni de seguridad.

## Decisiones y alcance

- Conservar los estados documentales según su ámbito: **CONFIRMADO** para objetivo y contexto institucional; **PROVISIONAL** para arquitectura lógica Edge + Plataforma, monolito modular, modelo lógico y stack candidato; **EN INVESTIGACIÓN** para detector, embedder y otros componentes biométricos; **PENDIENTE** para decisiones no cerradas; **APROBADO SOLO PARA PoC** para autorizaciones experimentales delimitadas; **REEMPLAZADO** y **DESCARTADO** cuando una decisión formal así lo establezca. Una autorización PoC no es selección definitiva ni evidencia de funcionamiento físico. No presentar propuestas, planes, diagramas o texto académico en pasado como funcionalidades verificadas.
- El responsable del proyecto aprueba el alcance de cada entrega y revisa previamente cambios importantes de arquitectura, reglas funcionales, modelo físico, tecnologías, contratos Edge y tratamiento de datos. Dentro de un alcance aprobado, desarrollar las decisiones ordinarias sin solicitar autorización por cada línea. Ante una contradicción con el baseline o una resolución, detener la parte afectada, explicar alternativas y esperar decisión; no resolverla por conveniencia.
- Trabajar sobre `main`. No crear ramas ni worktrees por iniciativa propia. **Solo el usuario realiza `git add`, commits y push**; no ejecutar estas operaciones ni cambiar remotos o historial.

## Desarrollo por módulos en tres bloques

- **Definición.** Antes de programar, consolidar alcance, reglas de negocio, permisos, criterios de aceptación, exclusiones y decisiones pendientes. Agrupar las preguntas necesarias para resolverlas conjuntamente cuando sea posible.
- **Implementación integral.** Tras aprobar el alcance, desarrollar en un encargo coherente las capas, componentes, contratos, pruebas y documentación necesarios. Resolver detalles técnicos rutinarios, corregir fallos de pruebas y no volver a solicitar autorización para acciones ya permitidas.
- **Validación y cierre.** Presentar resultados verificables y el incremento para revisión independiente. Reservar las operaciones MySQL reales, las migraciones y las acciones Git sujetas a autorización. Cerrar con un informe compacto de cambios, pruebas y pendientes.

## Arquitectura y dominio

- Mantener un monolito modular por capacidades: Identity/IAM, Personas, Accesos, Integración Edge, Auditoría y Consultas/Reporting. Dentro de cada capacidad, separar API/presentación, aplicación/casos de uso, dominio/reglas e infraestructura/persistencia cuando exista funcionalidad que justifique esas piezas. Las dependencias deben apuntar hacia dominio y casos de uso; Flask, ORM, MySQL y hardware no definen reglas de negocio. Evitar importaciones directas de repositorios internos de otra capacidad.
- Usar provisionalmente Python 3.14.x, Flask 3.1.x, SQLAlchemy 2.0/Flask-SQLAlchemy, Alembic/Flask-Migrate, MySQL LTS, React/Vite/Bootstrap y API web HTTP/JSON estilo REST bajo `/api/v1`. Sus versiones finales, endpoints y payloads concretos siguen sujetos a definición. Mantener un contrato OpenAPI legible por herramientas y versionado con la API cuando se implementen endpoints.
- `Persona` es el individuo; `UsuarioPlataforma` es una cuenta web distinta. Conforme a **ARQ-IAM-001**, incorporada en el Contexto Maestro v1.7, en el prototipo inicial no hay FK ni vinculación automática entre ambas entidades. La finalidad y cardinalidad de un vínculo futuro quedan PENDIENTES. Respetar los roles provisionales SUPERADMIN, ADMINISTRADOR y OPERADOR, con exactamente uno por cuenta. Solo SUPERADMIN administra cuentas y asigna o cambia roles; no se autoriza crear arbitrariamente más SUPERADMIN ni dejar la plataforma sin uno operativo. `ACTIVO` en Persona no significa acceso autorizado ni enrolamiento válido.
- Separar el registro administrativo de Persona del enrolamiento biométrico, según la resolución puntual aprobada. RegistrarPersona puede existir sin captura facial y no completa por sí solo CU-03. Personas no depende de cámara, Raspberry Pi, Hailo, detector, embedder ni plantillas biométricas.
- Para el primer incremento de persistencia, aplicar la resolución puntual **Registro de Personas y Persistencia MySQL** con estado PROVISIONAL: nombre y apellido principales, TipoPersona, tipo y número de documento obligatorios; identificador institucional nullable en MySQL, obligatorio para ESTUDIANTE y opcional para VISITANTE. La regla de SERVICIOS_GENERALES y las reglas especiales de otras categorías siguen PENDIENTES. Mantener `id_persona` interno, FK real hacia TipoPersona, unicidad del identificador institucional presente y unicidad compuesta de tipo y número de documento; estados ACTIVO/INACTIVO con ACTIVO inicial y timestamps UTC. No inventar el catálogo definitivo de tipos documentales ni añadir datos personales o biométricos ajenos al incremento.
- `ObservacionBiometricaEdge` es un resultado técnico; solo la Plataforma aplica reglas para producir, cuando corresponda, `EventoAcceso`. No guardar imágenes en observaciones. Mantener separadas la API web y la frontera Edge: protocolo, autenticación, contrato definitivo, sincronización y operación offline siguen PENDIENTES. El pipeline facial y las pruebas físicas pertenecen al ámbito Edge/experimentos, no a este repositorio.
- **ARQ-BIO-POST16-01 (PROVISIONAL, incorporada en v1.7):** el enrolamiento presencial Edge/HEF es la primera ruta experimental; el enrolamiento web por fotografía sigue PENDIENTE. El servicio lógico de enrolamiento se desacopla mediante puertos y adaptadores. La Plataforma es la autoridad lógica PROVISIONAL del ciclo de vida de plantillas integradas; la galería Edge integrada es derivada y versionada, no maestra. Usar conceptualmente referencias opacas, perfiles/versiones y estados `ACTIVE`, `REVOKED`, `OBSOLETE`, sin fijar almacenamiento físico. POC-XRUN-01 y la compatibilidad ONNX–HEF siguen EN INVESTIGACIÓN. Nada de ello acredita implementación biométrica integrada existente.

## Implementación, pruebas y seguridad

- Aprovechar del ejemplo del profesor la app factory, configuración externa, rutas ligeras, casos de uso, repositorios, validación, migraciones revisadas, pruebas de integración, cliente HTTP centralizado y componentes/páginas separados. No copiar su dominio, roles, registro público, SPA vanilla, JWT en `localStorage`, secretos, `debug=True` de despliegue ni commits desde cada repositorio.
- Cada caso de uso controla su transacción completa; los repositorios no hacen commits independientes. Revisar las migraciones antes de aplicarlas. Para integración MySQL, usar una base de pruebas **separada** de desarrollo, fallar si la configuración apunta a otra base y verificar el esquema mediante migraciones. Ninguna operación destructiva debe dirigirse a datos de desarrollo o producción.
- Mantener las pruebas existentes. Añadir pruebas significativas de éxito, validación, duplicidad, integridad referencial, permisos cuando correspondan, rollback y casos negativos; comprobar con MySQL real las restricciones que SQLite podría no reproducir. Informar qué se ejecutó y su resultado real; no afirmar que pasaron pruebas solo porque existen o pasaron históricamente.
- Gestionar secretos y credenciales mediante entorno y `.env` ignorado; `.env.example` contiene solo marcadores seguros. No introducir imágenes faciales, crops, embeddings, plantillas, contraseñas, tokens, credenciales ni datos sensibles reales en Git, logs, prompts o contextos de agentes, código, pruebas o entregas. Usar datos ficticios en pruebas. No crear tablas biométricas, endpoints Raspberry ni sincronización Edge–Plataforma sin aprobación específica.
- El login humano de Identity/IAM usa usuario y contraseña, independiente de la biometría. Guardar solo hashes resistentes; inicializar el primer SUPERADMIN mediante un procedimiento explícito e idempotente, sin contraseña fija ni efectos al importar Flask. Auditar acciones administrativas sensibles sin credenciales. No crear registro público de cuentas.
- Para usuarios humanos, seguir provisionalmente sesiones stateful del lado del servidor, identificador opaco en cookie `HttpOnly`, `Secure` y `SameSite`, y CSRF en cambios de estado. El backend autentica y autoriza; los guards del frontend solo apoyan la experiencia de usuario. No usar JWT en `localStorage` para humanos ni trasladar su mecanismo automáticamente a Edge. Auditar acciones sensibles según requisitos aprobados.

## Continuidad entre sesiones

Antes de reanudar, especialmente tras alternar Codex y trabajo manual: leer el último commit y `git status`; revisar los archivos modificados y su diff; identificar las pruebas disponibles y los resultados realmente obtenidos; contrastar el estado actual con el alcance aprobado y las decisiones vigentes. No sobrescribir ni descartar trabajo ajeno. Si el código cambió, ajustar el plan antes de editar. Al terminar, informar archivos tocados, comportamiento, verificaciones efectuadas, riesgos y decisiones pendientes. No atribuir requisitos a la encuesta al personal de seguridad, que no se aplicó.

## Preparación de sesiones, fuentes y verificación preventiva

### 1. Preparación documental de Codex

Antes de iniciar un nuevo incremento, preparar un manifiesto con el baseline vigente, las resoluciones aplicables, el alcance aprobado, los criterios de aceptación y el estado del repositorio. Codex debe confirmar que puede leer los documentos necesarios antes de realizar cambios que dependan de ellos. No asumir que los archivos disponibles en ChatGPT están disponibles automáticamente en Codex.

### 2. Fuentes funcionales y de datos

Durante el Bloque 1, el usuario y ChatGPT revisarán el modelo lógico, el Anexo 3 de diccionarios de datos del Entregable 3, el Contexto Maestro y las resoluciones aplicables. Las decisiones aprobadas se consolidarán en una especificación breve del incremento para entregarla a Codex; no es obligatorio adjuntar todo el Entregable 3 en cada nueva sesión. Validar los casos de uso, historias de usuario, tecnologías y descripciones de implementación de ese documento antes de adoptarlos. Conservar los nombres y conceptos del dominio y respetar las convenciones técnicas existentes.

### 3. Tres bloques y responsabilidades

Mantener los bloques de Definición, Implementación integral, y Validación y cierre. ChatGPT y el usuario coordinan la definición y la revisión independiente. Codex desarrolla el incremento aprobado, revisa su propio código, ejecuta las pruebas permitidas y corrige los errores que encuentre dentro del alcance autorizado. La autorrevisión de Codex no sustituye la revisión independiente posterior. Evitar comprobaciones repetitivas y la fragmentación innecesaria de tareas.

### 4. MySQL, respaldos y migraciones

Antes de operaciones reales que modifiquen bases de datos, comprobar dentro de procedimientos controlados la identidad del esquema, la revisión de migraciones, los permisos, los objetos MySQL y la compatibilidad del entorno Windows/Git Bash. Garantizar respaldos privados, completos y verificados cuando sean necesarios. Utilizar comprobaciones previas y posteriores, con autorización para las operaciones de escritura. No aplicar este procedimiento operativo completo a simples pruebas unitarias o cambios de código que no modifiquen MySQL.

### 5. Diagnóstico seguro de errores

Ante fallos, conservar la evidencia, identificar la etapa exacta y distinguir problemas de conexión, validación, rutas, permisos, entrada y escritura. No revelar credenciales ni información sensible. No realizar reintentos automáticos, restauraciones, eliminaciones ni cambios de privilegios improvisados. Corregir únicamente lo necesario y verificarlo antes de considerar un nuevo intento.

### 6. Revisión de código y Git

Codex debe revisar el código que implementa, sus pruebas, contratos y documentación. El usuario y ChatGPT realizarán posteriormente una revisión independiente de los cambios. Comprobar archivos modificados y nuevos, posibles secretos, respaldos, inconsistencias y finales de línea. Codex puede consultar Git; `git add`, commits y push quedan reservados al usuario. No ejecutar `git reset`, `git restore` ni otras operaciones Git de escritura sin autorización específica. El usuario conserva el control de los commits y del push.

### 7. Prevención de errores y calidad de código

- Separar las precondiciones de los verificadores por destino: `recon_tests` exige ausencia de residuos operativos; `recon_dev` conserva datos legítimos y compara sus huellas antes y después. No reutilizar validadores entre bases sin revisar todas sus precondiciones; probar aisladamente las rutas `--antes` y `--despues` de ambas bases antes de usarlas.
- Reproducir en pruebas locales aisladas los errores de conversión, consultas y transformaciones de SQLAlchemy, sin conectar MySQL. Por ejemplo, para convertir filas de dos columnas a diccionario, usar `dict(conexion.execute(...).all())`, no `dict(conexion.execute(...))`.
- Ejecutar Ruff desde la implementación, inicialmente sin correcciones automáticas, mediante `ruff check --isolated --no-cache --no-fix --select E4,E7,E9,F src tests scripts`. Revisar cada hallazgo y justificar exclusiones puntuales para fixtures de pytest o importaciones con efectos de registro.
- La validación final puede combinar pruebas unitarias, integración MySQL autorizada y Ruff, conservando las barreras de seguridad de cada una. Migraciones, respaldos y operaciones Git siguen procedimientos independientes sujetos a autorización; la revisión independiente y las pruebas reales son condiciones de cierre que las comprobaciones estáticas no sustituyen.
